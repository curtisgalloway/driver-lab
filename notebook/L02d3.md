# L02d3 — check qualification

Unit of the [plan](../IMPLEMENTATION-PLAN.md) (L02d); verdict record:
[evidence/L02d3.md](../evidence/L02d3.md). Terms: a **claim** is a check whose PASS L02f will
cite as evidence about the candidate; a claim is **qualified** when a planted defect that
violates it made that check fail, for that reason, with the valid control passing on the same
harness. See the [glossary](../GLOSSARY.md).

## 2026-09-25T14:23-07:00 — opening
Goal: freeze the claim set, then plant a defect per claim and record claim → defect → run ID,
or `unqualified` / `unobservable` / `insensitive` with the reason. Start: branch
`driver-porting/l02d3` from `origin/main` at `2ea7724`, in its own worktree; no local changes.
Private run store for this unit: a new directory beside L02d2's, same layout.
Approach: qualification runs each target scenario alone on fresh guests, so leftover frames
from an earlier scenario cannot reach it (the L02d2 contamination). No harness change is
planned unless a claim needs one.

## 2026-09-25T14:40-07:00 — decision: the claim set
24 claims (Q01–Q24) frozen in the evidence file, grouped by what the driver must do rather than
one per check name; stimulus checks (floods running, rings wrapped, harness writes, leftover
frames) are preconditions, not claims. The `itr` read-back is not a claim (C4). Committed before
any defect run.

## 2026-09-25T14:40-07:00 — surprise: the reference pads in software
The "pad bit cleared" defect proposed in L02d2 would be equivalent on its own: the reference
calls `eth_skb_pad` on every transmit before the device sees it, and its reset path also sets
TCTL.PSP. The padding defect must clear PSP in both places and drop the software pad.
