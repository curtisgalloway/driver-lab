# L02f1 — differential run and attribution

Unit of the [plan](../IMPLEMENTATION-PLAN.md) (L02f); verdict record:
[evidence/L02f1.md](../evidence/L02f1.md). Terms: the **candidate** is `e1000_l02`, written
from the spec alone (L02e); the **reference** is Linux v6.12's `e1000`. A **divergence** is a
difference between their results or register traces. See the [glossary](../GLOSSARY.md).

## 2026-09-25T15:09-07:00 — attempt: rounds c1 and r1
The reference passed all ten isolated scenarios (r1), so A4 holds for this session. The
candidate FAILed all ten (c1), each the same way: `insmod` succeeds, then probe returns
`-EBUSY` with "EEPROM direct access still granted (EECD=0x00000188)", so no interface
exists and every later check fails. Its whole trace is 8 writes and 11 reads: interrupts
masked, RCTL/TCTL cleared, a global reset through the memory BAR, two PHY ID reads, then
EECD read 0x188, written 0x188 (REQ clear), read 0x188 again, and the abort.

## 2026-09-25T15:09-07:00 — surprise: QEMU hard-wires EECD.EE_GNT
EECD bit 7 (EE_GNT) reads 1 with EE_REQ (bit 6) clear, at rest and after the candidate
releases REQ. QEMU 10.2.1's `get_eecd` (hw/net/e1000.c) ORs `E1000_EECD_PRES|E1000_EECD_GNT`
into every read, so no driver can ever see the grant drop. The reference never tests for it:
it sets REQ (0x1c8), bit-bangs, and clears REQ without checking GNT afterwards. The
candidate's step E1 treats GNT=1 as "direct access in progress" and gives up. Model
limitation for certain; whether the spec's E1 also asks for more than the manual does
needs the spec and manual text, which are in the run store, not on the test host.

## 2026-09-25T15:12-07:00 — attempt: rounds c2 and s1

## 2026-09-25T15:47-07:00 — decision: the probe failure is a model limitation
Manual §13.4.3 gives EE_REQ and EE_GNT an initial value of 0b; the §13.4.4 note says software
should ensure both are 0b before using EERD, since an EERD read can stall while direct access
is granted. Spec E1 transcribes that note, tagged and cited, so it is not a spec error. The
candidate follows E1: one release of REQ, one re-read, then `-EBUSY`. On a device that
behaves as the manual says, GNT reads 0 and probe continues. Label `benign` (manual
tie-breaker), cause model limitation. The candidate's single re-read with no wait and no
fallback is a robustness choice the spec left open; noted for L02f3, not called an error.

## 2026-09-25T15:47-07:00 — attempt: comparing the probe prefix
Only the probe up to E1 ran, so that is all the trace comparison covers. Both drivers mask
interrupts, clear RCTL and TCTL, then reset. The candidate resets through the memory BAR
(its default, `io_reset=0`), once, with a 9 µs gap to the next access; the reference resets
three times through the I/O window with gaps of about 5.9 ms. This is the first MMIO reset
the harness has recorded. Q18 (1 µs after reset) passed, and it is still unqualified. The
candidate reads the PHY IDs (0x0141/0x0c20) before the EEPROM; the reference's probe does
thousands of EECD bit-bang accesses, which work because QEMU always grants.

## 2026-09-25T15:56-07:00 — correction: reference reset count
The 15:47 entry "the reference resets three times through the I/O window" counted the whole
smoke run. Before its first EEPROM access the reference resets once, twice in its probe, and
three times across the run (the third at teardown). The gaps are unchanged.
