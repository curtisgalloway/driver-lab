# L02d3: check qualification

## Terms

- **Harness** — [`evals/e1000/harness/`](../evals/e1000/harness/), unchanged from L02d2
  unless stated below. **DUT**, **peer**, **register trace**, **deferred check** and
  **planted defect** are as in the [L02d2 evidence](L02d2.md#terms).
- **Claim** — a check whose PASS L02f will cite as evidence about the candidate driver.
- **Precondition** — a check that only confirms a scenario's stimulus happened (a flood ran,
  a ring wrapped, the harness's own register write succeeded). Preconditions make a claim's
  result meaningful; they are not evidence about the driver and are not qualified here.
- **Qualified** — a planted defect that violates the claim made its check fail, for that
  reason, while the unmodified reference passed the same scenario on the same harness.
- **Labels for the rest:** `unqualified` (no defect was planted, or none made the check
  fail), `unobservable` (QEMU's model cannot show the violation), `insensitive` (a defect
  that violates the claim was planted and the check still passed; a finding about the check).
- **Isolated run** — a harness run of one scenario on freshly booted guests, so frames left
  over from an earlier scenario cannot reach it.

See the [glossary](../GLOSSARY.md), the [design](../QEMU-DIFFERENTIAL.md) (§7, A6), the
[plan](../IMPLEMENTATION-PLAN.md) (L02d3), and the [notebook chapter](../notebook/L02d3.md).

## Claim set (frozen 2026-09-25, before any candidate run)

Frozen in this unit's first commit, before any defect was run. No candidate result exists:
the candidate has never been loaded (L02e). Check names are as they appear in
`verdicts.json`; a claim may cover the same check in several scenarios.

**Preconditions, not claims:** insmod and bound to a PCI device (a driver that cannot load
fails everything after it); no frames left over during bring-up; memory BAR found; the
harness's IMC and IMS writes; driver's interrupt mask read; flood running; the DUT was
transmitting when the link dropped; traffic flowed both ways when the interface went down;
the rings wrapped at least 3 times; the receive ring ran dry; while masked, the device
accepted frames and the driver wrote no RDT; no traffic while the link is down; HTTP server
started; and the `capture` pseudo-scenario's checks.

**Not claims:** the `itr` scenario's read-back compares QEMU's model with the trace decoder
and passes whatever the driver writes (L02d2 C4); ITR = 0 is legal (spec revision 4). The
observations (ITR values written, reset windows and gaps, ring bases above 4 GiB, ICR
link-change reads, TDH/TDT during an outage) are recorded for comparison in L02f, not judged.
