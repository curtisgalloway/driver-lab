# SF2-5: the viewer and publishing

**Terms:**

- *viewer*: the generated HTML reading copy of a spec (`spec.py render --format html`).
- *badge*: a small label in the viewer generated from a structured field, never from author text.
- *claim container*: the element holding one fact's author Markdown, kept apart from its badges.
- *mutation check*: remove or invert one guard in the code and confirm a test fails by assertion
  (not by a crash); a survivor is a guard no test pins.
- *Pages*: the static-site hosting the spec repositories publish to.

See the [glossary](../GLOSSARY.md) for the rest.

## What was built

- **Viewer (`render_html.py`):** each fact is an `article` with a `claim` container (author
  Markdown rendered with raw HTML disabled, images as links, link schemes limited, a fixed element
  set and no attributes taken from author text) and a `provenance` container of badges drawn from
  fields. An unbalanced construct ends at its field's container. The parser is a shallow copy of
  the checker's with HTML off, so the checker's HTML detection is unchanged.
- **Badges and stylesheet:** class, verdict, TODO, critical, origin, assumes, contested,
  requirement/assessment, and gap.
- **Publish workflow template (`skills/spec-format/ci/`):** builds both views, repeats the
  containment check, uploads an artifact on pull requests, and deploys to Pages on `main` and
  weekly. Permissions are read-only except the deploy job. Every action is pinned by full SHA.
  A build/verify helper regenerates the page inventory from the checked sources and compares every
  expected view byte for byte, in the build job and again in the deploy job, so a site missing a
  spec's page is refused.
- **Dry run:** the workflow's build steps ran against scratch fixture layouts, with no real deploy.

## Limitations and follow-ups

- **Deployment ordering.** The deploy job's concurrency group (`cancel-in-progress: false`)
  serializes deployments but cannot guarantee commit order when builds finish out of order, so
  an older commit's deploy could run last and publish an older site until the next push or the
  weekly run. The page shows its commit. A workflow-level group or a commit comparison would
  tighten it; not done. [GitHub documents the limit](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency).
- **Pages not enabled.** Enabling Pages in the spec repositories, installing the template there
  (including the context checkouts in both jobs, and replacing the zero tool-commit placeholder,
  which the build refuses) and the live site are SF2-11.
- **Literal fields.** Titles, TODO text, derivations, assumption text and readings render as
  literal text although `title` is a checked author-Markdown field, so Markdown in a title shows
  raw. A fenced code block in a claim draws a bordered box that resembles a badge, but it carries
  no badge class and sits in the labeled claim container.
- **Fail-closed refusals.** Headings in author text, and nesting beyond the parser's limit, make
  the viewer refuse the page rather than render it; the checker reports these separately.
- **Not exercised:** a real GitHub runner and a real Pages deploy; search and navigation
  (a design non-goal).
