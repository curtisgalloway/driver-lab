# L02f1: differential run and attribution

## Terms

- **Candidate** — `e1000_l02`, the driver written from spec revision 4 alone (L02e).
- **Reference** — Linux v6.12's `e1000` driver, which the candidate is compared with.
- **Isolated run**, **claim**, **qualified** — as in the [L02d3 evidence](L02d3.md#terms).
  Harness terms (DUT, peer, register trace, phase) are in the
  [harness README](../evals/e1000/harness/README.md#terms).
- **Divergence** — a difference between the candidate's and the reference's results or
  register traces, labeled per design §6: `bug`, `benign`, `suspect` or `ref-issue`, with the
  manual as tie-breaker, and given a cause: spec gap, spec error, implementation error, or
  model limitation.

See the [glossary](../GLOSSARY.md), the [design](../QEMU-DIFFERENTIAL.md) (§5–§6, A4, A5,
A7), the [plan](../IMPLEMENTATION-PLAN.md) (L02f), and the [notebook chapter](../notebook/L02f1.md).

## Status

**Complete, 2026-09-25.** All four rounds ran and one independent review of the raw runs
was applied (see Review). The candidate failed every scenario at probe, for one cause: the
QEMU model always reports the EEPROM grant bit set, and the candidate enforces spec step E1
(from the manual's §13.4.4 note) as a hard precondition and aborts probe. Nothing after probe
was exercised, so no behavior after probe has been compared.

**The one cause.** In every candidate scenario `insmod` succeeds and probe then fails:

```
e1000_l02 0000:00:01.0: EEPROM direct access still granted (EECD=0x00000188)
e1000_l02 0000:00:01.0: probe with driver e1000_l02 failed with error -16
```

No interface exists, so each scenario FAILs at "bound to a PCI device", then the MAC,
"interface up" and carrier checks (four failed checks each; `reload` fails the same four for
load 1). The kernel-log check passes (isolated runs: 9 lines, none flagged; `s1`'s later
scenarios: 5 lines). In all 20 isolated runs and in all ten of `s1`'s scenario logs, the
kernel log names this failure.

The candidate's entire register trace is 8 writes and 11 reads, identical in `c1` and `c2`:
IMC = all ones, RCTL = 0, TCTL = 0x8; STATUS read; CTRL read, CTRL written with RST through
the memory BAR, CTRL read; IMC again; ICR and STATUS reads; MDIC (4 reads, 2 writes) for the
PHY ID 0x0141/0x0c20; then EECD read 0x188, EECD written 0x188 (EE_REQ clear), EECD read
0x188, and the abort. EECD 0x188 is DO (bit 3), EE_GNT (bit 7) and EE_PRES (bit 8), with
FWE (bits 5:4) = 00b.

## Attribution

| Question | Answer | Source |
| --- | --- | --- |
| What does the manual require? | EE_REQ and EE_GNT have initial value 0b. "Software should ensure that EEC.EE_REQ = 0b and that EEC.EE_GNT = 0b as well before attempting to use EERD", because an EERD access "can stall until the EEC control has been released" | SDM §13.4.3 (EECD table), §13.4.4 note |
| What does the spec say? | Step E1: "Make sure EECD.EE_REQ = 0 and EECD.EE_GNT = 0 (no direct access in progress)", tagged `[databook]` and cited to that note; the EERD register section repeats it as a rule | spec revision 4, §5.3 E1 and the EERD section |
| What did the candidate do? | Released EE_REQ once, re-read once, and returned `-EBUSY` when EE_GNT was still 1 | trace, kernel log |
| What does the model do? | Reports EE_GNT = 1 on every EECD read, whatever EE_REQ holds: its EECD read handler ORs in the present and grant bits unconditionally | QEMU 10.2.1 `hw/net/e1000.c`, `get_eecd` (operator-side reading, permitted by the design's isolation rule) |
| Why does the reference pass? | It never uses EERD: it sets EE_REQ (EECD 0x1c8), bit-bangs the EEPROM, and never checks that the grant drops. A grant that is always 1 satisfies it | reference trace (about 6,700 EECD accesses per probe) |

**Divergences found, with labels (design §6).** Only the probe up to E1 ran on both drivers,
so this is the whole comparison. Causes are given as a primary cause and, where one applies,
a secondary one, so spec gaps stay separate from model limitations (A7).

| # | Divergence | Label | Cause | Notes |
| --- | --- | --- | --- | --- |
| V1 | Candidate aborts probe at E1; reference completes probe | `benign`; `[emulated]` result; open finding (A5) | model limitation (primary); spec gap (secondary): E1 gives no bound, fallback, or proceed-on-stall policy | By the manual the candidate's check is correct: the manual gives EE_GNT an initial value of 0b, and a device that behaves so passes E1. The manual's note is conditional ("if software has requested direct pin control") and names a stall, not an error, as the consequence; aborting with `-EBUSY` after one re-read is the candidate's own policy, which the spec leaves open. The model's EERD read does not consult EECD, so the grant would not have blocked an EERD read (from the model's source; not run). The grant never drops in this model, so waiting alone cannot succeed: a driver that waited with a bound and then proceeded, or fell back to direct access, would survive it. Blocks every scenario |
| V2 | EEPROM read through EERD (candidate) vs 4-wire EECD bit-bang (reference) | `benign` | none | Both are manual-permitted (SDM §5.3.1). The spec says to implement EERD first and add EECD only if EERD does not work on the test device: a development-time fallback, not a runtime one |
| V3 | Global reset before the EEPROM step: through the memory BAR, 9 µs to the next access (candidate), vs through the I/O window, about 5.9 ms (reference; one reset before its first EEPROM access, two in its whole probe) | `benign` | none | Manual rule (1 µs) met by both. The first memory-BAR reset the harness has recorded (no L02d2 or L02d3 run shows one). Q18 is unqualified (L02d3), so this is an observation, not qualified evidence |
| V4 | PHY ID read before the EEPROM (candidate); the reference reads STATUS twice, masks interrupts, reads STATUS and EECD (0x188), then masks again before clearing RCTL and TCTL | `benign` | none | Order within probe is not prescribed by the manual |
| V5 | After the reset the reference clears MANC's ARP-interception enable (MANC read 0x222300, written 0x220300); the candidate never touches MANC | `benign` | none | Spec revision 4 puts manageability ARP interception out of scope and says to skip it |

**A second model departure, not a divergence.** EECD reads with FWE (bits 5:4) = 00b, which
the manual lists as "not allowed" (initial value 01b), and both drivers write FWE = 00b: the candidate once
(the value it read, with EE_REQ cleared), the reference on every EECD write, about 5,040 in
probe. The spec says to leave FWE at
01b. Recorded as an `[emulated]` observation; for L02f3, E1 could say to preserve FWE = 01b
on the write that releases EE_REQ.

## Decisions

- **No repair, no workaround.** This unit has zero repair authority. Changing the model,
  the harness, or a module parameter to get past E1 would be a repair or a harness change,
  both outside L02f1. The candidate has no parameter that skips E1.
- **The comparison stops at probe.** A phase-by-phase trace diff (an operator-side analysis
  script kept in the run store) found nothing to compare past the EEPROM step.
- **Label V1 `benign`, not `bug`.** The manual is the tie-breaker and the candidate follows
  it. The label says the candidate is not wrong by the manual; it does not say the outcome is
  harmless: V1 blocks the whole evaluation in emulation.

## For L02f2

What a repair brief may carry (observations, no reference or QEMU source): "On the emulated
device, EECD reads 0x188 at rest and after EE_REQ is written 0: EE_GNT never reads 0." The
repair question is the candidate's policy when the grant stays set (wait with a bound, then
proceed; or fall back to direct access), which the spec leaves open. L02f2 needs the user's
repair budget and implementer choice (L02e's cap is spent). Until a repaired candidate binds,
nothing after probe has been tested.

  teardown. This run says nothing about them.
