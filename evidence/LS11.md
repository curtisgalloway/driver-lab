# LS11: firewall by name

**Terms:** the *hook* is `cleanroom_hook.py`, the check that runs before each tool call in an
implementation session and denies reads of encumbered source; the *implementer* is the role with
no `CLEANROOM_ROLE` set (the *investigator* and *verifier* roles may read, and every read is
logged); the *firewall by name* is the new rule that denies four names whatever the policy file
says; a *dirty-side skill* is a skill whose body maps into encumbered source (all in the
[glossary](../GLOSSARY.md) and the `cleanroom-skills` glossary). `review-swarm` is seven
reviewer subagents with distinct mandates and a referee.

Design: [LICENSE-SPLIT.md](../docs/LICENSE-SPLIT.md) (LS-R18, acceptance item 3). Plan:
[LS11](../docs/LICENSE-SPLIT-PLAN.md#ls11--firewall-by-name). Notebook: [LS11](../notebook/LS11.md).

## What changed (in `cleanroom-skills`, branch `license-split/ls11`, commits `199059a` and `35ff17e`)

- `scripts/cleanroom_hook.py`: a firewall for `board-expert`, `hardware-investigator`,
  `cleanroom-investigator` and `hardware-specs-gpl`. The names are a constant in the script, so a
  workspace policy that omits them cannot turn the firewall off; a policy may add names under
  `blocked_names`. The investigator and verifier roles follow the existing path: allowed and
  logged (`allowed-role`). `hardware-specs-docs` and `hardware-specs-permissive` are not matched.
- How a call is judged: by name, case-folded and URL-decoded, over path keys, command keys and
  (name only) every other argument key, which is what catches the `Skill` tool, a subagent prompt
  and an MCP `repo` argument. When the hook can see the filesystem (it passes the workspace as
  the working directory) it also resolves symlinks and `..`, expands globs on disk, expands
  `$VAR`, `${VAR}` and assignments (also after `export`/`declare`), undoes quoting and `{a,b}`
  braces, follows `cd`/`pushd` and a `Cwd` argument for relative reads, recurses into `sh -c`
  strings and `$( )` bodies, and scans a directory handed to a content-reading command
  (`grep -r`, `rg`, `find`, `tar`, `cp -r`) to four levels and 3,000 entries.
- `scripts/session_audit.py` is unchanged: it reuses `pick_target`, so a recorded session that
  read a firewalled name is flagged (text match only; no filesystem).
- Policy hardening found by the review: list-valued policy keys that are not lists of strings fall
  back to defaults, and blank entries in `authorized_roles` are dropped.
- Documentation: `SKILL.md` (a "Firewall by name" section with the limits), the standing-rules
  text in `agents-md-block.md` and `driver-implementer.md`, the policy asset's note, a
  `run_command` regex in `antigravity-permissions.json`, and the tests README.
- Tests: 32 new hook tests (`TestFirewallByName`, `TestFirewallWithoutNamingThePath`,
  `TestFirewallReviewFindings`) and 2 audit tests in `199059a` (61 to 95); 15 more in `35ff17e`
  (95 to 110), from the commit security review below.

## Limitations

- A name built at run time (`printf`, `base64`, slicing, a variable set in an earlier tool call)
  or a script file that performs the read is invisible to the hook. The sandbox tier is what
  closes the shell.
- A recursive search rooted more than four levels above a blocked directory is allowed (the one
  cap that does not fail closed); `grep -r` from a high ancestor is the likely shape. A tree of
  more than 3,000 entries, a glob of more than 5,000 matches and the other caps now deny the
  implementer instead (see the commit security review).
- A big workspace therefore denies `grep -r pat .` and similar until the path is narrowed; that
  is the price of failing closed.
- `cargo` and `make` are not treated as reading a directory argument. `git` scans for every
  subcommand except a short no-scan list (second review, below), skipping `.git` itself.
- Known false denials, chosen over a silent allow: a call with a `query`-style key and no path, and
  a `| grep` pipeline, scan the working directory, and a tree over the 3,000-entry budget (a large
  `target/` or `node_modules/`) denies them with the narrower-path message. Not narrowed: that is a
  design decision (second review, below).
- A search tool whose directory sits under a key the hook has no table for is resolved by name but
  not scanned below; an unknown-key value of 1,024 characters or more, or with whitespace, is matched
  by name only.
- Pattern-only search tools are checked against the working directory only when the hook is given
  one (never in the session audit, which has no filesystem).
- A copy made earlier by a role that may read the original is not a firewalled name.
- The workspace policy file is writable by the implementer; the built-in names and the blank-role
  handling hold, but a policy that lists a real role name in `authorized_roles` is believed. The
  environment tier should keep the policy file read-only to the implementer.
- A case-insensitive filesystem alias that differs by more than case is not matched.
- `antigravity-permissions.json` gets the four names only in its `run_command` regex.
- The whole-command match denies a command whose prose names a firewalled skill.
- The remote CI for `cleanroom-skills` is the orchestrator's to confirm.

## Commit security review

An automated review of the checkpoint commit `199059a` reported three items by summary line
only: "authorization-bypass / sibling-path parity", "fail-open resource cap", and a third without
a name. I examined both named items and everything near them; the third was not identifiable
from its summary, so I looked for fail-open behavior and form differences generally and list
what I found. Fixed in `cleanroom-skills` `35ff17e`, each with a test that failed on `199059a`
(10 failing tests of 15 new; the others are controls).

| Item | Finding | Resolution |
| --- | --- | --- |
| Fail-open cap | The directory scan's entry budget, the glob cap (truncated to 200 matches before resolving), the brace cap (truncated silently) and the shell-nesting limit (stopped analyzing) all allowed what they could not check | All raise a limit condition that denies the implementer with "give a narrower path" (investigator and verifier unaffected). Only the scan depth stays a documented allow. Tests: scan budget, glob, brace, nesting, deny message, investigator unaffected |
| Fail-open error | An unexpected exception while checking exited 1 (not a block on every harness) | The check is wrapped; an error denies. Test patches `pick_target` to raise |
| Parity | Grep/Glob with a pattern and no path were not checked against the working directory, a bare shell `grep -r pat` was | Such a call (pattern-like key, no path key) scans the working directory; with a path it uses that path. Tests in `TestFirewallFormParity` |
| Parity | An argument under a key the hook has no table for was matched by name only, so a symlink to a firewalled directory passed | Resolved like a path key when it names something on disk, without scanning below it |
| Parity | A `Cwd` argument was resolved against itself, so a symlinked working directory was caught only when a file inside it was named | The resolved working directory is checked by name before it becomes the base |
| Parity | `git add .` or `git -C .` scanned the directory argument, which with fail-closed would deny ordinary work in a large workspace, while `git grep pat .` must still scan | `git`, `cargo`, `make` skip the scan unless the segment runs a search tool |
| Sibling names | The suspected prefix-match inconsistency | The match was already a substring, applied the same in path, command, search and repo forms; a pinned test now shows `board-expert-notes`, `hardware-specs-gpl-main`, `hardware-specs-gpl.git` and `x-board-expert` denied alike in all four. I kept the substring rather than switching to component matching, because a component match would allow a renamed or suffixed copy of a blocked directory; the cost is that an unrelated sibling with the name inside it is denied too |
