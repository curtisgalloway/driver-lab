# L02d2: QEMU harness, scenarios and planted defects

## Terms

- **Harness** — [`evals/e1000/harness/`](../evals/e1000/harness/): a host-side Python driver
  and a guest init script that boot two QEMU guests and run named scenarios against them.
- **DUT** (device under test) — the guest with QEMU's emulated Intel 82540EM, whose driver
  module a scenario loads. **Peer** — the second guest, with a virtio-net card.
- **Reference driver** — Linux v6.12's in-tree `e1000`. The **candidate** (`e1000_l02`, from
  L02e) is not run in this unit; L02f runs it.
- **Register trace** — QEMU's log of every guest read and write to the e1000's registers.
  **Phase** — the guest command or host action a register access happened during.
- **Deferred check** — a check a scenario registers and the harness evaluates after QEMU
  exits, from the trace or the packet captures.
- **Planted defect** (mutation) — a deliberate bug in a disposable copy of the reference
  driver. An **equivalent mutation** changes the code without breaking any rule the manual
  states, so no manual-based test can or should fail on it.
- **Review swarm** — the `review-swarm` skill: seven reviewer agents with narrow mandates, a
  mechanical check that drops any finding it cannot quote from the code, and a referee.
- **Operator** — the coordinating agent session that wrote the harness and this record.
- **SDM** — the Intel 8254x Software Developer's Manual pinned in L02a.

See the [glossary](../GLOSSARY.md), the [design](../QEMU-DIFFERENTIAL.md) (§5–§7; O3,
O5, and the harness halves of A3, A4, A6), the [plan](../IMPLEMENTATION-PLAN.md) (L02d,
L02d2), the [L02d1 evidence](L02d1.md), and the [lab notebook chapter](../notebook/L02d2.md).

## What was built

- **Nine scenarios** beyond `smoke`, covering the design's §5 list: `frame-sizes`,
  `ring-wrap`, `rx-overrun`, `link-flap`, `link-loss-tx`, `stop-start`,
  `down-during-traffic`, `reload`, `itr`. `--scenario all` runs the ten in order; a suite run
  takes about 133 s with KVM. Each is described in the [harness README](../evals/e1000/harness/README.md#scenarios).
- **A kernel-log check after every scenario**, taken after the driver is unloaded: warnings,
  call traces, oopses, transmit hangs, netdev watchdog timeouts, interrupt storms, DMA-API and
  allocation failures fail the scenario. This closes the L02d1 limitation.
- **Trace decoding and per-phase grouping for L02f:** every register access decoded to the
  manual's register name (I/O-window accesses resolved to the register `IOADDR` selected) and
  labeled with its scenario and phase, in `dut-regtrace.jsonl`; per-phase access counts in
  `trace-phases.json`.
- **Trace rules from the manual**, checked over the whole trace: at least 1 µs between a
  global reset and the next register access (SDM 13.4.1); ring lengths nonzero multiples of
  128 (13.4.27, 13.4.38); ring bases 16-byte aligned; tail writes inside the ring (3.2.6,
  3.4); head writes only while that direction is disabled (13.4.28, 13.4.39); ITR's reserved
  bits clear (13.4.18). A reset returns lengths and enables to power-on values (14.7).
- **Deferred checks** that prove each scenario created its condition: tails wrapping, the
  DUT's frame lengths in the peer's capture, traffic in the trace in the second before a link
  or interface drop, ITR read-back against the last write.

## Decisions

- **ITR read-back (L02b finding C-2).** Read through the memory BAR with busybox `devmem`, and
  compared by a deferred check with the last ITR write in the trace, or with 0 after a global
  reset. This checks that the device model and the trace decoder agree; it does not test the
  driver, since a driver that never writes ITR, or writes a wrong value, still passes (C4).
  The values the driver wrote before the read-back are recorded as an observation for L02f.
  Spec revision 4 allows ITR = 0.
- **Receive overrun in emulation.** QEMU's e1000 does not drop and count frames when the
  receive ring is full; it stops accepting them, and the backlog pushes back to the peer. There
  is no missed-packet count or overrun cause to observe. The scenario instead masks the DUT's
  interrupts (the harness writes IMC, then restores IMS), floods it, and requires the receive
  head to reach the tail (SDM 3.2.6) before reception resumes. A model limitation for the
  proposed `[emulated]` evidence class.
- **m1 is an equivalent mutation.** The design's first example, "receive tail written one
  descriptor early", hands the device one fewer buffer. The manual lets software hand over
  any number of descriptors (SDM 3.2.6), and the reference already holds one back. It is kept
  in the record, undetected as predicted, and m5 plants the defect the example was reaching
  for: the tail written only on the first fill after load.
- **Floods are `ping -i 0.001`.** This busybox's `nc` has no UDP mode, and `ping -i 0` hangs
  the guest. Each flood is checked to be running, and the trace must show traffic in the
  second before the link or interface drops.
- **Neighbor entries are flushed after a link outage**, after being recorded: pings sent while
  the link was down leave the ARP entry unresolved, and the next ping can be lost waiting for
  a fresh resolution. That is the stack's behavior, caused by the scenario.
- **DUT memory 3 GiB**, so that memory above 4 GiB exists for L02e's DMA-mask question (M2).

### Planted defects (round 5, run in parallel with r010)

A scenario whose bring-up received more than 4 frames left over from an earlier stalled
flood is **contaminated**: its failure may be the earlier scenario's effect, and it is not
counted as a detection by this one. Passing the 4-frame limit does not prove a scenario was
isolated either, so failures after a stalled flood are at most "not independently
attributable" unless their own trace shows the defect. How many leftovers reach which
scenario varies with timing (m5's link-flap saw 0 in round 3 and passed; 254 in round 4 and
failed before toggling the link).

| Defect | Direct detection | Contaminated failures | What caught it |
| --- | --- | --- | --- |
| m1 receive tail one early | none | none | equivalent mutation; valid control |
| m2 transmit descriptors without RS | all ten scenarios | — | pings lost; "Detected Tx Unit Hang" in the kernel log |
| m3 interrupt mask not restored after polling | all ten scenarios | — | pings lost; netdev watchdog timeouts in the kernel log |
| m4 receive ring length one descriptor short | ring-wrap, rx-overrun, link-loss-tx, down-during-traffic; trace rules | link-flap (47 frames), stop-start (158) | RDLEN 0xff0 and RDT 0xff in a 255-descriptor ring; traffic lost once the ring wraps. `smoke` passes |
| m5 receive tail written only on the first fill | ring-wrap | rx-overrun (82), stop-start (157), down-during-traffic (5), reload (255, 85); link-loss-tx failed with no excess leftovers but after a stalled flood, so it is not independently attributable | reception stops once the first fill is used: RDT never wraps. In round 4, down-during-traffic had 4 leftovers and its own trace showed the receive stall (no RDT write while its flood's frames were accepted): a detection of the stall, not of a fault in the down/up transition. link-flap passed (0 leftovers). `smoke` passes |

m4 and m5 are the cases the design's scenario list exists for: both pass the smoke test.

### Observations for L02f (reference driver, rounds 3 to 5)

  there.

## Open limitations

- The kernel-log patterns are a fixed list; a fault that logs something else passes.
- The 1 µs reset rule measures QEMU's processing times, not bus timing; under KVM each
  register access costs microseconds, so a driver with no wait could still pass it.
- Receive overrun counters (MPC, RNBC) and the overrun cause cannot be observed in QEMU.
- `--accel tcg` still untested.
- Packet checks match frames by content only: `filter-dump` timestamps are not on the host
  clock (28,796 s apart in the L02d1 capture checked).
- The peer uses the same kernel as the DUT.
- **Most checks have never been shown able to fail** (C9): frame-sizes' capture checks,
  itr, link-flap's carrier check, stop-start, reload, and the gap, base, head and ITR trace
  rules failed only as a side effect of total transmit loss or not at all. Two §7 examples
  are half covered (RS only; receive ring only). Proposed defects: pad bit cleared with no
  software padding, TDLEN one short, LSC left out of IMS, ITR never written, no post-reset
  delay. FCS insertion is invisible in these captures.
- The 1 µs reset rule cannot fail for resets through the I/O window, which is how the
  reference resets (C7). stop-start never stops a live link (C8).
- L02e item L4 cannot be reproduced in QEMU; M2 was not probed with the reference, which
  uses a 32-bit DMA mask here.
- **Leftover frames contaminate later scenarios.** A defect that stalls a flood leaves frames
  queued at the peer, which arrive at the next bring-up. The check names the cause, but it
  cannot tell whether that scenario would also have caught the defect. Killing the peer's
  sender is not enough (the cleanup already does); verified draining of the peer and its
  transport backlog, or fresh-guest reruns of single scenarios, are inputs to L02d3.
